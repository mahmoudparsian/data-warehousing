# 🟦 Exploratory Data Analysis (EDA)
## Profile the Data Before You Trust It

EDA = a **systematic profile** of new data **before** it is cleaned, modeled or reported.

👉 One question: **"Can we trust this data for analytics, and what must Silver fix?"**

---

# 🏗️ Where EDA Fits (Medallion Architecture)

| Layer | Holds | EDA's job |
|---|---|---|
| 🥉 Bronze | raw files, as they arrived | **profile**: find the problems |
| 🥈 Silver | cleaned, typed, deduplicated | turn each finding into a **rule**, then re-check |
| 🥇 Gold | star schema, KPIs | trust the numbers because Silver was checked |

Without EDA: wrong KPIs, broken dashboards, bad decisions. **Garbage in → garbage out.**

---

# 🔍 Six Kinds of Checks

| # | Check | Question | SQL |
|---|---|---|---|
| 1 | **Structure** | which columns, which types, same in every file? | `DESCRIBE`, `union_by_name` |
| 2 | **Completeness** | how many values are missing? | `COUNT(*) - COUNT(col)` |
| 3 | **Uniqueness** | duplicates? a usable key? | `COUNT(DISTINCT …)` |
| 4 | **Distribution** | range, center, spread, spikes | `MIN`, `MEDIAN`, `quantile_cont`, `MAX` |
| 5 | **Validity** | values in the allowed list / range? | `NOT IN (…)`, `NOT BETWEEN` |
| 6 | **Semantics** | does the value make **business** sense? | a question for the data owner |

Today, all six on **4 yearly insurance files** (`data/insurance.2021.csv` … `2024.csv`).

---

# 🔧 Load All Four Files (Bronze)

```sql
CREATE OR REPLACE TABLE ins AS
SELECT * EXCLUDE (filename),
       regexp_extract(filename, '(\d{4})', 1)::INTEGER AS year   -- lineage: which file?
FROM read_csv('data/insurance.*.csv', filename = true, union_by_name = true);

SELECT year, COUNT(*) AS n_rows
FROM ins
GROUP BY year
ORDER BY year;
```

<!-- RESULT -->

| year | n_rows |
|-----:|-------:|
| 2021 |   1540 |
| 2022 |   1300 |
| 2023 |   1549 |
| 2024 |   1732 |

*(4 rows)*

<!-- /RESULT -->

- `filename = true` keeps the source file; we turn it into a `year` column, or the 4 years are mixed with no way back.
- 💡 2022 has about 250 rows fewer than its neighbours: a smaller year, or a **missing part** of the file? Ask before you report a trend.

# 1️⃣ Structure: Columns and Types

```sql
DESCRIBE ins;
```

<!-- RESULT -->

| column_name | column_type | null | key  | default | extra |
|-------------|-------------|------|------|---------|-------|
| age         | BIGINT      | YES  | NULL | NULL    | NULL  |
| gender      | VARCHAR     | YES  | NULL | NULL    | NULL  |
| bmi         | DOUBLE      | YES  | NULL | NULL    | NULL  |
| children    | BIGINT      | YES  | NULL | NULL    | NULL  |
| smoker      | BOOLEAN     | YES  | NULL | NULL    | NULL  |
| region      | VARCHAR     | YES  | NULL | NULL    | NULL  |
| charges     | DOUBLE      | YES  | NULL | NULL    | NULL  |
| year        | INTEGER     | YES  | NULL | NULL    | NULL  |

*(8 rows)*

<!-- /RESULT -->

- `union_by_name = true`: if one year had an extra or a missing column, we would see it here (a NULL-only column).
- `smoker` (`yes` / `no` in the files) is read as **BOOLEAN**.

---

# 2️⃣ Completeness: Missing Values

```sql
SELECT COUNT(*)                   AS n_rows,
       COUNT(*) - COUNT(age)      AS missing_age,
       COUNT(*) - COUNT(gender)   AS missing_gender,
       COUNT(*) - COUNT(bmi)      AS missing_bmi,
       COUNT(*) - COUNT(smoker)   AS missing_smoker,
       COUNT(*) - COUNT(region)   AS missing_region,
       COUNT(*) - COUNT(charges)  AS missing_charges
FROM ins;
```

<!-- RESULT -->

| n_rows | missing_age | missing_gender | missing_bmi | missing_smoker | missing_region | missing_charges |
|-------:|------------:|---------------:|------------:|---------------:|---------------:|----------------:|
|   6121 |           0 |              0 |           0 |              0 |              0 |               0 |

*(1 row)*

<!-- /RESULT -->

💡 No NULLs. A clean result is a **finding** too: write it down, so next year's load can be compared with it.
(`SUMMARIZE ins;` shows NULL % and more for every column at once.)

---

# 3️⃣ Uniqueness: Duplicates

The files have **no customer id**, so the only test is: is a whole row repeated **within the same year**?

```sql
SELECT COUNT(*)                                                               AS n_rows,
       COUNT(DISTINCT (year, age, gender, bmi, children, smoker, region, charges)) AS distinct_rows,
       COUNT(*) - COUNT(DISTINCT (year, age, gender, bmi, children, smoker, region, charges)) AS duplicate_rows
FROM ins;
```

<!-- RESULT -->

| n_rows | distinct_rows | duplicate_rows |
|-------:|--------------:|---------------:|
|   6121 |          5899 |            222 |

*(1 row)*

<!-- /RESULT -->

💡 **222 rows** are exact copies of another row in the same year: double-loaded records. Every count, sum and average is inflated.
No key also means we **cannot** follow one customer from year to year.

---

# 3️⃣ Uniqueness: Conflicting Duplicates

Same year, same person, same charges, but a **different region**? `DISTINCT` cannot catch these: the rows are not identical.

```sql
SELECT regions, COUNT(*) AS pairs
FROM (SELECT year, age, gender, bmi, children, smoker, charges,
             list(region ORDER BY region) AS regions
      FROM (SELECT DISTINCT * FROM ins)
      GROUP BY ALL
      HAVING COUNT(DISTINCT region) > 1)
GROUP BY regions
ORDER BY pairs DESC;
```

<!-- RESULT -->

| regions                | pairs |
|------------------------|------:|
| [northeast, southeast] |   287 |
| [northeast, northwest] |   221 |
| [northeast, southwest] |   167 |

*(3 rows)*

<!-- /RESULT -->

💡 **675 pairs (1,350 rows)**, and **every** pair has one copy in the **northeast**: a customer cannot live in two regions in the same year.
The northeast's row count, smoker count and average are all inflated. Which copy is right? Only the **source system** can tell: ask, and flag both copies until then.

---

# 4️⃣ Distribution: Range, Center, Spread

```sql
SELECT ROUND(MIN(charges), 0)                  AS min,
       ROUND(quantile_cont(charges, 0.25), 0)  AS p25,
       ROUND(MEDIAN(charges), 0)               AS median,
       ROUND(AVG(charges), 0)                  AS avg,
       ROUND(quantile_cont(charges, 0.75), 0)  AS p75,
       ROUND(MAX(charges), 0)                  AS max
FROM ins;
```

<!-- RESULT -->

|   min |    p25 |  median |     avg |     p75 |     max |
|------:|-------:|--------:|--------:|--------:|--------:|
| 200.0 | 9025.0 | 14816.0 | 18455.0 | 26047.0 | 61974.0 |

*(1 row)*

<!-- /RESULT -->

💡 The average is far above the median: a **right-skewed** distribution (a few very expensive customers).
And the minimum is a suspiciously **round** number: next slide.

---

# 🔎 Distribution: Look for Spikes

```sql
SELECT ROUND(charges, 2) AS charges, COUNT(*) AS n_rows
FROM ins
GROUP BY ALL
ORDER BY n_rows DESC, charges
LIMIT 3;
```

<!-- RESULT -->

| charges | n_rows |
|--------:|-------:|
|   200.0 |     76 |
|   406.8 |      2 |
|  659.39 |      2 |

*(3 rows)*

<!-- /RESULT -->

💡 Charges have cents, so almost every value is unique, except **exactly $200.00**, which appears **76 times**.
A spike at a round value usually means a **default**, a **minimum fee** or a **placeholder**, not a real measurement.

---

# 5️⃣ Validity: Allowed Values and Ranges

```sql
SELECT COUNT(*) FILTER (WHERE gender NOT IN ('male', 'female'))                                   AS bad_gender,
       COUNT(*) FILTER (WHERE region NOT IN ('northeast', 'northwest', 'southeast', 'southwest')) AS bad_region,
       COUNT(*) FILTER (WHERE age NOT BETWEEN 18 AND 100)                                         AS bad_age,
       COUNT(*) FILTER (WHERE bmi NOT BETWEEN 10 AND 70)                                          AS bad_bmi,
       COUNT(*) FILTER (WHERE children NOT BETWEEN 0 AND 10)                                      AS bad_children,
       COUNT(*) FILTER (WHERE charges <= 0)                                                       AS bad_charges
FROM ins;
```

<!-- RESULT -->

| bad_gender | bad_region | bad_age | bad_bmi | bad_children | bad_charges |
|-----------:|-----------:|--------:|--------:|-------------:|------------:|
|          0 |          0 |       0 |       0 |            0 |           0 |

*(1 row)*

<!-- /RESULT -->

💡 Every value passes. **Valid is not the same as correct**: the 76 rows at $200.00 pass every range check.

---

# 6️⃣ Semantics: Does It Make Business Sense?

```sql
SELECT year,
       COUNT(*)                         AS rows_at_200,
       COUNT(*) FILTER (WHERE smoker)   AS smokers,
       MIN(age)                         AS min_age,
       MAX(age)                         AS max_age
FROM ins
WHERE charges = 200
GROUP BY year
ORDER BY year;
```

<!-- RESULT -->

| year | rows_at_200 | smokers | min_age | max_age |
|-----:|------------:|--------:|--------:|--------:|
| 2021 |          19 |       0 |      18 |      54 |
| 2022 |          13 |       0 |      18 |      63 |
| 2023 |          17 |       0 |      18 |      32 |
| 2024 |          27 |       0 |      18 |      40 |

*(4 rows)*

<!-- /RESULT -->

💡 76 customers, **no smokers**, ages 18–63, in every year: a business rule we do not know (a minimum premium?) or a placeholder for "unknown".
**Ask the data owner**, write the answer down, then decide in Silver: keep, flag, or set to NULL.

# 🧭 From EDA Findings to Silver Rules

| Check | Finding in these files | Silver rule |
|---|---|---|
| Structure | same 7 columns every year; no year column | add `year` from `filename` (lineage) |
| Completeness | no NULLs | none; re-check on every load |
| Uniqueness | **222** exact duplicate rows; no customer key | remove exact duplicates (`DISTINCT`) |
| Uniqueness | **675** pairs that differ only in `region` (always one in the northeast) | flag both copies; ask the source which region is right |
| Distribution | right-skewed charges; spike at **$200.00** (76 rows) | report the **median** too; flag `charges = 200` |
| Validity | all values in range | keep the checks as **tests** |
| Semantics | what does $200.00 mean? 2022 is smaller (and has no conflicting pairs) | ask the data owner; document the answer |

# 🚀 Best Practices

- Profile **every** column, in **every** file, on **every** load (not only the first time).
- Keep the source file name (`filename = true`): every finding needs "which file?".
- Count before and after every cleaning step: rows in = rows out + rows removed.
- **Write the findings down**: template in [`more_examples/data_exploration_TOC.md`](more_examples/data_exploration_TOC.md).
- Separate "invalid" (fails a rule) from "suspicious" (passes the rules, but someone should look).

# ✅ Summary

| Check | Key SQL |
|---|---|
| Structure | `DESCRIBE`, `read_csv(…, union_by_name = true, filename = true)` |
| Completeness | `COUNT(*) - COUNT(col)`, `SUMMARIZE` |
| Uniqueness | `COUNT(*) - COUNT(DISTINCT (col1, col2, …))` |
| Distribution | `MIN`, `quantile_cont`, `MEDIAN`, `AVG`, `MAX`; `GROUP BY value ORDER BY COUNT(*) DESC` for spikes |
| Validity | `COUNT(*) FILTER (WHERE col NOT IN (…) / NOT BETWEEN …)` |
| Semantics | look at the rows, then **ask** |
